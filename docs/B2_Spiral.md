# B2 Spiral controller and directional target

**Decision:** ADR-002 + ADR-003 · **Controller:** `b2-controller-3` · **Direction policy:** `b2-direction-1-conservative` · **Runtime:** one pinned Falcon-H1-Tiny 90M Instruct Q4_K_M GGUF in one browser Worker. These version names identify code paths; they are not evidence of a reasoning gain.

## Directional state contract

The user's B2 vision is **not** a fixed `Falcon → answer → check → retry` pipeline. The target is `Problem → structured mathematical state → B2 Compass direction → selected operation → independently checked progress → unresolved residual → new direction or stop`. Falcon is the language engine. B2 is responsible for dependency tracking, operation choice, verification, residual-only repair, stopping and exact R1 reuse. A fact becomes established only with a relevant independent receipt; the remaining residual stays visible. If one node fails, already verified nodes are retained. A repeated hypothesis or unchanged residual triggers a no-progress brake.

Compass ranks *eligible operations* using evidence for goal attraction, expected verified progress, information gain, compute cost, error risk and proven memory reuse. Each candidate/selection should record a score version, evidence scope, applicability and measured cost. Missing evidence stays unknown; no untested model-name or “magnetic” intuition is promoted. “Magnetic” means mathematical/software direction scoring. Basic exact calculators, verified local tools, Falcon generation and exact shared-state reuse can be candidate operations. Advanced/matrix, Level 3 psychological/magnetic, virtual calculators and B2CCP remain **unavailable or shadow research** until actual browser-compatible correctness, security and resource evidence exists.

This is the **target contract**, not a statement that the browser app already implements generalized mathematical state, a fully calibrated six-factor Compass, nested dependency graph or all calculator levels. `app/js/b2-direction.mjs` now exposes a narrow `createSpiralState` record (`parts`, `verifiedFacts`, `unresolved`, `residuals`, `visitedDirections`, model-call budget), ranks eligible exact/structured/local/Falcon operations, and records `direction`/`direction_result` trace entries. The six scores are explicit **engineering priors**; `expectedProgress` uses a category operation profile only after at least three checked local outcomes. The fixed safety tier prefers deterministic candidates and is a safety constraint, not measured superiority. `app/js/main.mjs` persists a bounded `spiral_state` message metadata snapshot and category `operations` counters inside `spiral_calibration_v2`. Matrix, psychological, virtual and B2CCP capabilities are unavailable. This narrow implementation must be evaluated on new cases before any quality claim. See `decisions/ADR-003-directional-spiral.md` for the full target contract and `B2_V2_Evaluation_Protocol.md` for the earlier evaluation method.

Every Send enters `SpiralController.run()` through `app/js/main.mjs`. `planSpiral()` classifies the task, chooses a bounded simple or complex budget, and records subtask IDs, dependencies and completion criteria. A simple exact expression uses the local two-parser calculator. A narrow, explicit syllogism, contradiction or missing-quantity grammar uses deterministic reasoning. Other simple tasks use one Falcon call. Multi-part complex tasks may use multiple Falcon hypotheses; the same model serves every part. Planning subtask splitting is braked pending better quality evidence; it uses one model hypothesis and an optional repair.

The UI defers loading Falcon into the runtime Worker until a turn actually needs language generation. Exact arithmetic and the narrow deterministic logic path can answer without loading model weights into inference memory. The model still must be provisioned and verified in browser storage before Send enables. `tools/browser_b2_lazy_load_smoke.mjs` asserts zero `load` commands after an exact answer and exactly one when chat generation starts.

Falcon may propose only allowlisted local tools. `tool-runner.mjs` validates and executes the proposal in a disposable Worker with a deadline; model text is never executable authority. Deterministic exact results may be marked verified. Open-ended prose and heuristic topic checks remain unverified. A failed exact check or denied tool proposal records the failing part and residual; the controller can retry within a maximum of four model calls. This version does not run arbitrary code, web search, local document search or a general theorem prover.

V2 correctness rules: every tool receipt, including failures, remains visible in the answer and trace. A mixed failed/successful set is unverified. A successful exact tool operation verifies only its own calculation; the overall answer is verified only when the user's exact requested expression independently matches. Exact candidate checking rejects conflicting numeric claims and explicit negation of the correct result. Repeated failed model text triggers `no_progress` and ends the repair loop.

For requests that explicitly ask for an explanation **and** an exact expression, Falcon can generate a hypothesis first. B2 checks the final numeric component independently and sends the precise mismatch into one bounded repair attempt. A corrected number does not verify the prose explanation; the full answer remains unverified. With **Think deeper** on a plan, B2 similarly identifies unmet explicit step/risk/topic constraints and targets only those in the repair prompt. Structural compliance is never promoted to semantic correctness.

For a complex planning request with **Think deeper** enabled, a second candidate is generated only when the first misses explicit surface constraints such as requested step count or risk mention. The controller compares coverage and records both scores. An automatic second candidate regressed UI latency without improving the observed plan, so it remains behind the explicit depth control. This is a provisional selection heuristic, not verification of a plan's practical correctness. Planning and coding still need stronger independent validation and human-reviewed tasks.

`ExactSpiral` retains exact expression identity, proven commutative equivalence, conversation scope, checksum replay and corruption repair. Cache hits and calculator operations are counted separately. The main thread persists run plan, trace, verification status, model calls, calculator calls, tokens, first visible answer and elapsed time in the message and local run events. `spiral_calibration_v2` stores per-category run counts, verified successes, checked failures, unverified outcomes, calls, latency and repairs. It is separate from the prior v1 record, so rollback can select the old key. At least three independently checked outcomes are needed before checked failures can raise the repair budget from one to two. This changes software budgets only and does not train weights or promote model policies.

The repair-budget comparison uses `verifiedModelSuccesses` and `verifiedModelFailures`, which count only turns where Falcon actually generated tokens. Pure calculator or rule-based successes remain in overall reporting but cannot make the model appear more competent. The public evaluation harness passes no calibration input and uses an isolated browser profile; held-out answers never update the local policy.

Benchmark commands: `npm run test:b2` for fixed development probes and browser smoke; `npm run test:b2:heldout` for a separate phrasing set. Each uses the same pinned Instruct weight, browser Worker and sampling temperature for Falcon alone and Falcon plus B2. Qualitative regex scoring is a weak proxy; inspect raw answers and failed cases in `evidence/`. Process-tree RSS includes the browser and Node harness, so it is not a model-only allocation measurement. Physical mobile, battery and thermal acceptance still require hardware.

`node tools/browser_b2_benchmark.mjs --combined --counterbalanced` alternates the A/B run order across the existing 22 fixed cases and reports category scores, verification status, repairs, latency, tokens, operations, cache hits and sampled process-tree memory. Both sets have been exposed to development and are **not independently held out**. A larger externally prepared, human-graded benchmark and isolated model memory measurement remain acceptance gaps.

The frozen 48-task public-source evaluation and disjoint 24-task confirmation set, their objective checkers, and blinded review procedure are specified in `B2_V2_Evaluation_Protocol.md`. The clean confirmation run checked 18 math/logic/contradiction/coding tasks and found Falcon-alone and Falcon+B2 both correct on 6; B2 took 193,196 ms versus 180,133 ms for Falcon alone, about 7.3% longer. Six plan/conversation pairs still require blinded human grades. These public tasks may have appeared in pretraining. This is no proof of general reasoning improvement; limited direction selection/verifier coverage/calibration are plausible explanations, not established root causes. The full negative receipts and repair-probe failures remain in `CHECKPOINT_LOG.md` and `evidence/`.
